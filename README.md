# 漢字書き取りドリル

iPad(Apple Pencil)で漢字を手書きし、**KanjiVG のお手本の筆画と 1 画ずつ照合して**合否を判定する書き取りドリルです。
サーバー処理のない静的サイトで、GitHub Pages や Cloudflare Pages にそのまま置けます。

- **テスト(出題の範囲)ごとに語をまとめる**: 「1 学期 中間テスト」のようにテストを作り、写真 10〜20 枚分の語をまとめます。
  取り込んだ語は選んでいるテストに入り、出題もそのテストの中からだけ行います。テストの中では写真ごとにまとめて表示し、写真ごとに出題する・しないを切り替えられます。
- **バックアップ・ほかの端末と共有**: すべてのテストをファイルに書き出し、読み込めます。iPad で書き出したファイルを AirDrop や iCloud Drive で iPhone に渡して「読み込んで合わせる」と、
  両方の端末のテストと語をまとめます(同じ語は、新しく出題・変更した方の成績を残します)。写真は保存しないので、データは 1 テスト(約 200 語)あたり約 50KB です。
- **表のプリント(四角で囲む)**: 縦書き・番号付きの列・書き取る部分がカタカナの漢字テスト(例:「重大ジケン」「奥地をタンケンする」)を撮影し、
  表を四角く囲むと、罫線から 1 問ずつ自動で切り出して読み取り、カタカナの部分を書き取る部分として自動で選びます。
  問題が何段に並んだ表(1〜14・15〜28・29〜40 番など)でも、列の区切りが点線でも読めます。
- **3 種類の問題**: 1 枚のプリントに混ざった問題を、種類ごとに出題します(読み取ったあとでタップで変えられます)。
  - **書き取り**: カタカナの部分を漢字で書く(これまでどおり)。
  - **読み**:「翡翠(読み)」のように「(読み)」と書かれた問題。漢字を見て、**読みをひらがなで手書き**します。ひらがなも KanjiVG のお手本と照合して判定します
    (送りがななど、語と同じかなはマスにせず文字で表示。例: 苛まれる → 「さいな」を書く)。読みは辞書(kuromoji)で引いて入れるので、違うときは直してください。
  - **百人一首**:「花の色は」のような初句を百人一首 100 首と照合して歌を選びます(「わたの原 や」のような手がかりの字で、初句が同じ歌も見分けます)。
    出題では初句(と、そのかな)を見て、続きを**ひらがなで入力**します。歴史的仮名遣いのまま 1 字ずつ比べて自動で判定し、
    答えの歌を漢字とかなの 2 段で表示して、違っていた字を赤で示します(例: 「ふきとじよ」と入力 →「ふきと**ぢ**よ」の「ぢ」が赤)。
    判定のあとの「参考」で、全日本かるた協会「一日一首」のその歌のページ(歌人・現代語訳・出典・決まり字・札)を窓に表示します。
- **問題プリント(なぞって選ぶ)**: ほかの形式のプリントは、問題を 1 問ずつ指や Pencil でなぞると、なぞった部分だけを読み取ります。
  書き取る部分(ひらがな)をタップで選ぶと、読みから答えの漢字の候補(天井・天上…)を出すので、正しいものを選びます(手で入力も可)。
- **文章**: 漢字を含む文章を写真から OCR で読み取り(Tesseract.js v5、`jpn` / `jpn_vert`)、kuromoji.js で漢字を含む語を取り出して読みを付けます。貼り付けだけでも使えます。
- 一覧で語・読みを直したり、出題する・しないを切り替えたりできます。
- 読みと前後の文脈を見て、漢字の字数ぶんのマスに手書きする(送り仮名はマスにせず、文字で表示)。
- 判定の厳しさは「超甘い・甘い・標準・シビア」から選べます(初期値はシビア)。画面はライト・ダーク・自動(端末の設定に合わせる)を選べます。
- 判定は「手書き文字認識で何の字か当てる」方式ではなく、お手本との照合です。似た字(日/曰、末/未、士/土 など)を正解にしません。
- 不合格の理由を筆画の番号付きで表示し、字の上に赤で示します。判定後はお手本(筆画番号付き)を並べて表示します。
- 語ごとに結果を保存し、語の一覧を色分けします。まだ合格していない語は、続けて間違えた回数で **1 回: 黄、2 回: オレンジ、3 回以上: 赤**。
  合格した語は緑で「**○ 3 回目で合格**」のように、何回目で合格したかを表示します(合格したあとでまた間違えたら、1 回目から数え直します)。
- 「全問出題する」「不合格の語だけ出題する」「3 回以上間違えた語だけ出題する」「未出題の語だけ出題する」を選べます。
- 設定画面の「1. 問題を取り込む」「2. 出題する語」「4. バックアップ」は、見出しをタップして開け閉めできます(開け閉めは端末ごとに覚えます)。全問終わったら結果画面に、その回の全問を同じ色分けで表示します(各回の成績の履歴付き)。

## ローカルで動かす(Windows)

Node.js 20 以降が必要です。

```bash
npm install
```

```bash
npm run serve
```

- PC では `http://localhost:8080/` を開きます。
- 同じ LAN の iPad からは、起動時に表示される `LAN: http://192.168.x.x:8080/` を Safari で開きます。
  開けない場合は、Windows のファイアウォールで Node.js の受信(プライベート ネットワーク)を許可してください。
- ホーム画面に追加すると、全画面で使えます(Safari の共有ボタン →「ホーム画面に追加」)。

`vendor/` と `data/` は生成済みのものがリポジトリに入っています。作り直す場合は、次を実行します。

```bash
npm run build:vendor
```

```bash
npm run build:data
```

読みの辞書(`data/yomi/`)は `node scripts/build-yomi.mjs` で作り直せます(`npm install` で入る mecab-ipadic-seed と joyo-kanji を使います)。

`build:data` は KanjiVG のリリース zip(r20260714 の main 版)をダウンロードして変換します。
展開済みの `kanji/` ディレクトリがあれば、`node scripts/build-kanjivg.mjs <kanji ディレクトリ>` でも作れます。

## 表のプリントの読み取り

縦書きで、番号付きの列が罫線で区切られ、書き取る部分がカタカナで書かれた形式(例:「重大ジケン」「提出キゲン」「姿をアラワス」)に合わせた読み取りです。

1. **表を四角で囲む**(囲まなければ写真全体)。表が 2 つあるプリント(右に漢字の表、左に百人一首の表など)は、1 つずつ囲んで「読み取る」を押すと、問題が後ろに足されます。局所しきい値で白黒にし(影・明るさのむらに強い)、縦の罫線がいちばんまっすぐに揃う角度を探して、写真の傾きを直します。
2. **罫線から列を切り出す**: 横の罫線で段に分け、背の高い段(いちばん高い段の 0.7 倍以上)を問題の段とします(番号の段・答えの段は低い)。
   縦の罫線は段ごとに探し(段ごとに列の位置が違ってもよい)、縦の罫線の間を 1 問として、上の段の右から順に 1 問目、2 問目…とします。
   罫線は、線の太さ方向に ±2px 広げて数えた黒の割合が 0.4 以上で、まわり(8〜14px 離れた所)より 0.3 以上高い所とします。点線(割合 0.5 前後)も見つかり、
   字の列(幅が広く、まわりとの差が 0.25 以下)は罫線と間違えません。本のページの湾曲で曲がった横線(番号の段・答えの段との区切り)も、
   列ごとに「横幅いっぱいに続く線」(点線の切れ目はつながっているとみなす)として見つけて、番号と手書きの答えを除きます。罫線を消し、紙を真っ白・字を真っ黒にしてから、縦書きの 1 行として読みます。
   名前の欄(「氏名」「一年 組 番」)と見出し(「百人一首」)は、問題として出しません。
3. **読み違いの補正**: カタカナの中に混ざった形の似た字(力→カ、工→エ、二→ニ、口→ロ、一→ー など)と、「コウェエン」のような小さい字の重なりを直します。
4. **書き取る部分を自動で選ぶ**: カタカナの並びをすべて選びます。読み(ひらがな)から答えの漢字の候補を出し、前後の文脈で並べます。
5. **問題の種類を決める**: 「読み」「(読み)」で終わる問題は読み(括弧は読み取りで消えることがあるので、なくてもよい)、カタカナがなく百人一首の初句に合う問題は百人一首、それ以外は書き取りです。

3 段・40 問の表と、百人一首 4 首の表が並んだプリントの写真では、2 つの表を別々に囲んで、**40 問と 4 首をすべて正しい順番で切り出せました**。
読みの問題 8 問と百人一首 4 首は、すべて正しい種類になりました(4 首とも正しい歌を 1 位に選択)。
カタカナの書き取りの部分はおおむね正しく読めますが、「翡翠」「犍陀多」「苛」のような画数の多い字・めずらしい字は読み違えることがあるので、「問題の語」の欄で直してください。

いただいた写真(10 問、少し傾いて、ページが湾曲したもの)では、**書き取る部分のカタカナを 10 問すべて正しく読めました**。
答えの候補の 1 位は 9 問で正解でした(事件・危険・探険・期限・保護・厚着・農耕・渡航・講演。「探検」は 2 位)。
「姿をアラワス」は「姿」を「次」と読み違えたため、正解の「現す」は 4 位でした。漢字の読み違いは文脈の表示と候補の順番にしか影響しないので、文字欄で直すか、候補をタップしてください。

## 問題プリントの読み取り(なぞって選ぶ)

漢字テストのプリントは、形式がいろいろ(傍線・括弧とふりがな・解答欄つき、縦書き・横書き)なうえ、**答えの漢字が画像の中にありません**。
写真全体を OCR すると、表の線や番号やふりがなが混ざって、意味のない文章になります。そこで、次のようにしています。

1. **なぞった帯だけを切り出す**: 帯の幅が 1 行分になるように拡大し、帯の外は白くします。帯の端にかかった問題番号や枠線(大部分が帯の外にある塊)と、
   文字の向きに沿った長い直線(傍線・下線・括弧の線)も消します。これをしないと、OCR が線を別の行として読み、意味のない文字を作ります。
2. **1 行として読む**: 帯が縦長なら縦書き(`jpn_vert`、1 ブロック)、横長なら横書き(`jpn`、1 行)で読みます。記号・数字・括弧は取り除きます。
3. **書き取る部分を選ぶ**: 読み取った文を 1 字ずつのボタンで表示します。辞書に載っている、いちばん長い仮名の並びを最初に選んでおくので、違っていたらタップで直します。
   1 問に書き取る部分が 2 か所ある場合も、両方を選べます。読み取りが間違っていたら、文字欄を直します。
4. **答えの漢字の候補**: 読みを辞書(mecab-ipadic から作った `data/yomi/`)で引き、送り仮名・活用語尾を残す形(だまって → 黙って)や、
   2 語に分けた形も作ります。候補を前後の文に当てはめて、kuromoji で文の自然さ(コスト)を比べ、常用漢字でない字や 2 語をつないだ形は後ろに回して並べます。
   1 位を答えとして入れておくので、違っていれば候補をタップするか、手で入力します。

いただいた実際のプリントの画像(解像度の低いスクリーンショット)でも、書き取る部分は 7 問中 6 問を正しく読めました(残る 1 問は「てんじょう」→「でんじょう」)。
単体テストの 16 例では、正解の漢字がすべて候補の 1 位でした。辞書にない複合語(例: ぎゅうどん → 牛丼)は候補に出ないので、手で入力してください。

## 判定のしくみ

入力はユーザーの筆画(書いた順)とお手本の筆画です。順に次を確認し、どれかに引っかかったら不合格にします。

1. **画数**: 違えば、その場で不合格にします(「画数が違います(正解 5 画 / あなた 4 画)」)。
2. **正規化**: お手本とユーザーのそれぞれをバウンディングボックスで 0〜1 に収めます。
   通常は縦横を別々に伸ばします(stretch)。お手本の短辺/長辺が 0.22 未満の字(「一」など)は、縦横比を保って中央に置きます(uniform)。
   stretch のときは、お手本の (w/unit, h/unit) で座標に重みを掛けてから距離を測ります。
   各筆画は弧長で等間隔に 24 点へ再サンプルします。
3. **割り当て**: コスト(mean + 0.5 × max(始点距離, 終点距離)、しきい値を超えるペアは +0.3)が最小になる割り当てを、ハンガリアン法で求めます。
   コストは逆向きに比べた場合も考慮します。「書き順も判定する」がオンのときは、i 画目をお手本の i 画目に固定します。
   書き順だけが違う場合は「書き順が違います(形は合っています)」と出します。
4. **字全体のアフィン補正(追加)**: 割り当てた対応点から、最小二乗のアフィン変換(リッジ正則化付き)を 1 回だけ求めて補正し、割り当てをやり直します。
   補正量が大きすぎるときは「字全体が傾いています」「字全体の形がゆがんでいます」で不合格にします。
5. **筆画ごとの比較**: 対応点の平均距離(mean)・最大距離(max)・始点と終点の距離・長さの比・始点→終点の角度を、しきい値と比べます。
   不合格の筆画は逆向きにして比べ直し、それで合格するなら「書く向きが逆です」とします。
6. **平行な筆画の長さの関係(追加)**: 長い筆画 2 本の向きがほぼ同じで、お手本で長さがはっきり違う場合、その長さの比が保たれているかを見ます(末/未、士/土)。
7. **字全体の縦横比**: stretch のときのみ確認します(日/曰)。
   バウンディングボックスの比は、はみ出した 1 画に引きずられるので、対応点のアフィン回帰で「お手本 → ユーザー」の横と縦の倍率を求め、その比で判定します。
8. **字ごとの追加ルール**: 日・曰(縦横比の許容差を狭くする)、午・牛(縦画が上に突き出るか)、刀・力(ノの書き始めの高さ)、己・已・巳(下記)。

判定の厳しさは「超甘い・甘い・標準・シビア」の 4 段階です(以前の「超シビア」はなくし、選んでいた場合はシビアになります)。
標準・シビアの mean〜縦横比の列は、依頼時の初期値から**変えていません**。調整は、数値を緩めるのではなく、判定の手順を足す形で行いました(理由は「調整の経緯と理由」の節)。

**甘い**(あとから追加)は、字の形のゆれ(位置・長さ・角度)を大きく許す一方、似た字を見分けるチェック(平行な筆画の長さの関係・字ごとのルール・己已巳の境界)は標準と同じ強さに残しています。
形のしきい値だけを一律に緩めた案では、雑に書いた字の合格率は 98% になりましたが、末/未・士/土 で 50%、牛→午 で 96% が誤って合格したため、採用しませんでした。
採用した値では、雑に書いた字の 90.8% が合格し(標準は 78.4%)、紛らわしい字の誤合格率は標準と同じくらい(最大 14.5%)です。
標準の「字ごとのルールの係数」は、甘いより見分ける力が弱くならないよう、1.3 から 1.2 に揃えました。

**超甘い**は、形のゆれをさらに大きく許します。実際の手書きでほぼ不合格になるという声を受けて、もっと大きなゆれ(部品の位置・大きさ、筆画の端のはね)で調べ直しました。
いちばん多い不合格の理由は「2 本の平行な筆画の長さの関係」だったので、超甘いでは、この確認は長さの関係がはっきり逆のときだけにしました。
大きなゆれで書いた字の合格率は 78% から 96% になりました。その代わり、横画の長さだけが違う字(士/土・末/未)は、超甘いでは見分けません(甘い以上で見分けます)。
画数の違いと、干/千・人/入・午/牛・刀/力 のように形がはっきり違う字は、超甘いでもほぼすべて不合格です。

**書いた筆画の手直し**: 画数がお手本より多いときは、判定の前に次のように直します(判定の結果の下に、直したことを表示します)。
- ちょんと触れただけの小さな点(字の大きさの 4% 未満)は除きます(どの厳しさでも)。触れた点 1 つで画数が違って不合格になるのを防ぎます。
- 甘い・超甘いでは、途中でペンを離して 2 画になった筆画をつなぎます(前の画の終わりと次の画の始まりが字の大きさの 6% 以内で、向きが続いているとき。
  3% 以内なら角で離してもつなぐ)。待/侍 のような、画数が 1 つ違う似た字は見分けたままです。

### 調整の経緯と理由

| 段階 | シビア・ふつうの合格率 | シビアの誤合格率(最大) | 変更と理由 |
|---|---:|---:|---|
| 1. 仕様どおり(初期値) | 63.0% | 13%(已→己) | 失敗の大半が mean・始点・終点でした。字全体の回転・せん断はバウンディングボックスの正規化では消えず、全筆画の位置の誤差として乗っていました。 |
| 2. アフィン補正を追加 | 93.4% | 28%(士→土) | 字全体のゆがみは吸収できました。ただ、しきい値の中で、上下の横画の長さの違い(末/未・士/土)も見逃すようになりました。「一」は点が一直線に並ぶので最小二乗が退化し、0% になりました → リッジ正則化を追加しました。 |
| 3. 平行な筆画の長さの関係を追加 | 91.8% | 19%(己→已) | 末/未・士/土 は 0% になりました。残りは 日/曰 と 己/已/巳 です。 |
| 4. 己・已・巳 のグループルール(境界 50%)、縦横比を回帰で推定 | 92.1% | 29%(曰→日) | 己→已 は 11% まで下がりました。縦横比はバウンディングボックスの偏りがなくなりましたが、日/曰 の差(対数で約 0.4)が全体の許容差(±42% = 0.35)とほぼ同じなので、かえって誤合格が増えました。全体の許容差を狭くすると、すべての字の合格率が下がります。 |
| 5. 日・曰 だけ縦横比の許容差を 0.2 に、己已巳 の境界を 32% に | 92.0% | 3.5%(日→曰) | 目標(合格率 90% 以上、誤合格 5% 以下)を満たしました。己・已・巳 は下記のとおりです。 |

**己・已・巳 について**: 3 画目(㇟)の書き始めの高さしか違わず、その差は 1 字の約 1/9 です。
模擬の手書きでは、筆画ごとのずれ(平行移動・拡大・回転)により、この高さが 1 字の約 1/18(σ)ばらつきます。
そのため、他の筆画を基準にした位置だけでは 10% 前後が重なります。
そこで、ばらつきの源が違う 2 つの特徴を、線形判別で 1 次元のスコアにまとめました。

- 3 画目の「書き始めから角までの弧長 ÷ 全体の弧長」: 筆画ごとの平行移動・拡大の影響を受けません。
- 1 画目の書き始めからの高さの差

3 字のお手本のスコアのうち、ユーザーの字のスコアに近いものを比べ、隣の字までの距離の 32%(シビア)を超えて離れたら「「已」に見えます」のように出します。
誤合格は 5% 以下になりましたが、その代わり、この 3 字は**正しく書いても**シビアで 57〜85% しか合格しません(3 画目の書き始めをはっきり書く必要があります)。
厳しすぎると感じたら、「合格にする」ボタンか「標準」を使ってください。

**注意**: 模擬の手書きの「ふつう」のゆらぎは、このプロジェクトで決めたものです。実際の手書きとの対応は、実機で確かめる必要があります。
実際の手書きでは、筆画のつなぎ目(己の 3 画目が 2 画目の左端から出るなど)が独立のずれよりも正確なので、己/已/巳 は模擬より区別しやすいはずです。
一方、お手本と字形の癖が違う人(とめ・はねの長さ、点の向き)は、シビアで不合格が増える可能性があります。

### そのほかの限界

- 短い筆画(点など、お手本の長さ 0.2 未満)は、長さを比ではなく差(シビアで 0.15)で見るので、比較的ゆるめです。
- KanjiVG に収録されていない字(〇、CJK 拡張 A のほとんどなど)は自己採点になります。
- OCR の精度は写真しだいです。読み取り結果はテキスト欄で直してください。

## GitHub Pages に公開する

1. GitHub で新しいリポジトリを作り、このフォルダの中身を push します(`node_modules/` は `.gitignore` 済み。`vendor/` と `data/` は含めます。公開されるファイルは合計約 32 MB で、最大のファイルは 5.9 MB です)。

   ```bash
   git init -b main
   ```

   ```bash
   git add -A
   ```

   ```bash
   git commit -m "漢字書き取りドリル"
   ```

   ```bash
   git remote add origin https://github.com/<ユーザー名>/<リポジトリ名>.git
   ```

   ```bash
   git push -u origin main
   ```

2. リポジトリの **Settings → Pages → Build and deployment → Source** で **GitHub Actions** を選びます。
3. `main` に push するたびに `.github/workflows/pages.yml` が動き、単体テスト(`npm test`)が通ったら、公開用のファイルだけを `_site/` に集めて公開します。
   手動で動かすときは、**Actions → GitHub Pages に公開 → Run workflow** を使います。
4. 公開先は `https://<ユーザー名>.github.io/<リポジトリ名>/` です。すべて相対パスなので、サブパスでもそのまま動きます。

### Cloudflare Pages の場合

ビルドコマンドなし、出力ディレクトリ `/` で公開できます(`tests/` などのファイルも配信されますが、動作には影響しません)。
kuromoji の辞書(`.dat.gz`)が `Content-Encoding: gzip` 付きで配信されても読めるよう、`vendor/kuromoji/kuromoji.js` にパッチを当ててあります。
gzip の先頭バイト(1f 8b)を見て、展開済みなら展開を飛ばします。

## 実装の注意点(以前の試作の落とし穴への対応)

- kuromoji の `dicPath` は相対パス(`vendor/kuromoji/dict/`)を渡します。絶対 URL だと内部の `path.join` で `https:/` に壊れるためです。
- kuromoji の辞書の二重展開への対策は上のとおりです(`scripts/copy-vendor.mjs` でパッチ。`tests/unit/vendor.test.js` で両方のケースを確認)。
- Tesseract.js の `workerPath` / `corePath` / `langPath` は自分のオリジンに向けます。
  `corePath` はディレクトリ(`vendor/tesseract/core/`)で、`tesseract-core-simd-lstm.wasm.js` と `tesseract-core-lstm.wasm.js` を置いています。
  言語データは `.traineddata.gz`(4.0.0_best_int)に統一し、`gzip: true` にしています。
- 写真は最初の `drawImage` で長辺 2400px に縮小してから処理します(12MP 以上でも canvas のメモリ制限に当たらない)。
  EXIF の向きは、Image で読み込んで canvas に描くことで、ブラウザに反映させています。
- 通信の失敗・OCR の失敗は画面上部にメッセージを出し、テキストの直接入力や語の手動追加で続けられます。
- 手書きは Pointer Events を使い、`touch-action: none`、`setPointerCapture`、`getCoalescedEvents` を使っています(使えない場合は通常のイベント)。
  `setPointerCapture` が効かない環境に備えて、`window` の `pointerup` でも筆画を閉じます。

- [ ] 丁寧に書いた字が「シビア」でおおむね合格する(厳しすぎる字があれば、字と理由をメモしてください)
- [ ] 語の一覧が、合格(緑・何回目で合格)・1 回まちがい(黄)・2 回(オレンジ)・3 回以上(赤)・未出題(灰)で色分けされ、「不合格の語だけ出題する」で不合格の語だけが出る
- [ ] テストを作って切り替えると、語の一覧と出題がそのテストの語だけになる。アプリを開き直しても、選んでいたテストのまま
- [ ] 写真を取り込むたびに「写真 1」「写真 2」…とまとまり、写真ごとに出題する・しないを切り替えられる
- [ ] 「書き出す」で共有メニューが開き、AirDrop で iPhone に送れる/「ファイル」に保存できる
- [ ] iPhone で「読み込んで合わせる」から、受け取ったファイル(「ファイル」アプリ)を選べて、同じテストと成績が入る
- [ ] 両方の端末で出題したあと、書き出し → 合わせるを行うと、新しい方の成績が残る
- [ ] 「未出題の語だけ出題する」で、まだ出していない語だけが出る
- [ ] 画面の「ライト」「ダーク」「自動」が切り替わり、アプリを開き直しても選んだ表示のまま(開いた瞬間に別の色にならない)
- [ ] 「合格にする」「書けた/書けなかった」(お手本データのない字)が動く
- [ ] 結果画面の「間違えた語だけもう一度」「全部をはじめから」「設定に戻る」と、成績の履歴
- [ ] ボタンが押しやすい(誤タップしない大きさ)。縦向き・横向きの両方で、マスや送り仮名のレイアウトが崩れない
- [ ] ホーム画面に追加すると、アイコンが表示され、全画面(アドレスバーなし)で起動する
- [ ] 通信を切った状態で「語を取り出す」や OCR を押すと、エラーメッセージが出て、手入力で続けられる
